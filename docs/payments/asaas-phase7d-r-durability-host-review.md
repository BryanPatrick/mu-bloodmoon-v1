## Current code path and transaction boundaries

`RechargeWebhookController.asaasWebhook` rate-limits and extracts `asaas-access-token`. `CommerceService.handleAsaasWebhook` first requires Asaas plus webhook-processing flags, validates the token, validates event ID/topic/payment ID, then calls `PaymentWebhookEventService.recordAndClaim`. That service inserts a minimized, PII-masked event row; `(provider, topic, eventId)` is unique. Only a `PROCESSED` duplicate short-circuits. A duplicate of a still-`RECEIVED` or `FAILED` row returns `retryable`, so concurrent deliveries can both perform provider lookups/processing. The handler then performs Asaas GET, checks provider identity and local recharge/customer/reference/amount, calls `reconcileAsaasOrder`, and marks the event `PROCESSED` or `FAILED` **before** returning HTTP 200. Provider GET has a 15-second abort timer. This entire HTTP flow is **not one DB transaction**: event insert, lookup, transition and final event-status update are separate boundaries. `transitionRechargeStatus` itself runs the wallet credit and recharge update inside one serializable transaction with bounded retry; the wallet ledger's business key `recharge-credit:<RechargeIntent.id>` is unique.

`PaymentWebhookEvent` is currently an **audit/claim record, not a complete durable inbox**. It has `RECEIVED`/`PROCESSED`/`IGNORED`/`FAILED` status usage, `receivedAt`, `processedAt`, `processingError`, sanitized `rawPayload`, `externalOrderId`, and optional `rechargeIntentId`. It lacks a processing lease, attempt count, next retry time, pollable ownership, and restart sweeper. Its current `retryable` outcome is not an exclusive processing claim. `RECONCILE_REQUIRED` is a distinct creation/recovery state on `RechargeIntent`, not a webhook queue status.

[Asaas's current receiving guide](https://docs.asaas.com/docs/receba-eventos-do-asaas-no-seu-endpoint-de-webhook) recommends persisting by event ID, returning HTTP 200, then processing asynchronously. [Its timeout guidance](https://docs.asaas.com/docs/erro-read-timed-out) gives a 10-second response window; [its paused-queue guidance](https://docs.asaas.com/docs/fila-pausada) says only 200 counts as success and 15 consecutive failures interrupt that webhook queue. The existing 15-second provider timeout alone exceeds that window, before DB and wallet work. Synchronous processing is therefore not an acceptable unmeasured production ACK strategy.

## Decision: DURABLE_INBOX_THEN_ACK — design only

Evolve the **existing** `PaymentWebhookEvent` table. Reject an in-memory queue or HTTP 200 before a committed event row. The ingress should authenticate, validate bounded identifiers/body, atomically insert or find the unique provider event, then return 200 only after durable commit. On DB failure, return non-200 and rely on provider redelivery. Target normal persist-plus-ACK latency **at most 1 second**, subject to local and future host measurement; this is an internal target, not a claim of observed performance. Continue provider GET before any financial transition; webhook payload is a notification, not settlement authority.

An independently enabled, DB-polling worker can reuse this application's `OnModuleInit`/bounded `setInterval` pattern, but must be off by default. Add only necessary immutable migration fields: status, `attemptCount`, `nextAttemptAt`, `leaseOwner` (opaque random worker ID), `leaseUntil`, `lastErrorCode`, `startedAt`, and completion time. Keep the existing unique tuple and minimized `rawPayload` (event ID/topic/payment ID only; never token, full billing payload or unnecessary PII). A short transaction or atomic conditional `UPDATE ... WHERE status IN ('RECEIVED','RETRY') AND nextAttemptAt <= now AND (leaseUntil IS NULL OR leaseUntil < now)` must elect one worker; check affected-row count. A crashed `PROCESSING` row with an expired lease becomes claimable again. Renew a lease only with matching owner; complete/retry only with matching owner. Use bounded exponential retry with jitter and a finite escalation threshold; a terminal `MANUAL_REVIEW`/`FAILED` state requires human action and an alert, not silent event loss. Make polling batch size, interval, lease duration and retry cap configurable. Two-process behavior must be tested on **both** MySQL and MariaDB rather than assumed from an ORM call. An external queue/Redis/n8n is not required for correctness.

The handler/worker should preserve correlation by `PaymentWebhookEvent.id`, provider event ID, provider payment ID and `RechargeIntent.id`, plus the existing recharge correlation ID. Log fixed event/error codes and opaque IDs only; never token, API key, document, name, email or full payload. The existing email and generic webhook alert channels are the simplest delivery path; local loopback delivery passed in Phase 7C, but no production recipient/delivery is proven. Approved initial owner: finance/payment operations; fallback: API operations. Approved configurable baseline: immediate credit failure after confirmed receipt, exactly-once breach, provider-auth failure; provider 5xx >=5/5 min, invalid webhook auth >=5/5 min, `RECONCILE_REQUIRED` older than 15 min, `MANUAL_REVIEW` older than 30 min. These conditions are **not** implemented by this document.

The worker should invoke the **existing** Asaas provider GET and `reconcileAsaasOrder` path. `RECONCILE_REQUIRED` remains the creation-ambiguity/recharge recovery state; the inbox reports *delivery processing* and does not create a competing payment state machine. Retention duration and purging rules remain Bryan's decision before public enablement.

## Crash and retry matrix for the proposed design

| Interruption | Required outcome |
|---|---|
| Before durable insert | No 200; provider retries. No local event or credit. |
| Insert commits, ACK lost | Provider retries; unique tuple resolves to the same row. Worker processes once logically. |
| 200 sent, process crashes before work | Committed `RECEIVED` row is polled after restart. |
| Provider GET times out | No credit; leased event enters `RETRY` with bounded backoff after lease expiry/worker error; ACK was already sent. |
| Provider GET succeeds, crash before transition | Lease expires; a new attempt re-queries provider and uses the existing transition. |
| Local wallet/recharge transaction commits, crash before event `PROCESSED` | Retry may re-query provider, but the recharge transition and unique wallet idempotency key prevent a second credit; worker marks the event complete. |
| Concurrent/sequential duplicate delivery | Unique event tuple prevents a second row; atomic lease avoids simultaneous workers; unique wallet key is the independent financial backstop. |
| App restart with `PROCESSING` | Expired lease is reclaimed; pending rows must be picked up without an in-memory-only signal. |

These are **acceptance requirements**, not passing tests. Before implementation is eligible for review, test concurrent and sequential duplicate deliveries, ACK-loss/redelivery, slow provider GET after safe ACK, two workers on each DB engine, crash/restart recovery, and one final wallet credit. Add a new migration only; do not modify an applied migration. Then rerun all relevant MySQL/MariaDB migrations and E2E suites, Asaas tests, wallet concurrency, API units and secret scan. No implementation was made in this phase because these acceptance conditions cannot honestly be marked green from a design alone.
