# Asaas Phase 7B — deployability and observability closure

This is a **local, inert candidate**, not a production release. No production credential, webhook registration, payment, deploy, database write, merge or push is authorized by this phase. Phase 7 history remains in `asaas-production-readiness.md`; its compiled-preview failure is resolved locally by inlining Nuxt UI's `tailwindcss/colors` dependency in the Nitro server bundle. Tailwind 3.4.19 did contain `colors.js`; the failure was an extensionless CJS subpath externalized into a Node ESM runtime, not a missing package. Verify the exact built artifact after any future clean install/Node version change.

## Independent controls and safe configuration

Use `deploy/.env.production.example` as a **placeholder template**, never as a production secret file. Intended inert state: `ASAAS_ENABLED=false`, `ASAAS_ENVIRONMENT=production`, exact production base URL, `ASAAS_FRONTEND_ENABLED=false`, `ASAAS_PAYMENT_CREATION_ENABLED=false`, `ASAAS_WEBHOOK_PROCESSING_ENABLED=false`, `ASAAS_RECONCILIATION_ENABLED=false`, `NUXT_PUBLIC_ASAAS_FRONTEND_ENABLED=false`, and `NUXT_PUBLIC_REAL_MONEY_PAYMENTS_ENABLED=false`; omit production provider credentials. Missing values fail closed. `ASAAS_ENABLED=true` alone never authorizes creation. The API requires *both* frontend and creation flags for new customer/payment POSTs. Browser flags merely hide UI; the API gate is authoritative. Webhook processing and admin reconciliation are independently gated so in-flight payments can be recovered while new creation is off; they must remain off in the first inert deployment unless a later approved plan explicitly turns them on.

Local HTTP tests use synthetic tokens and mock provider, with no real-provider network. The webhook route returns 401 for missing/wrong token and 200 for a valid synthetic token with an unknown event (no provider lookup, credit, or real transaction). The direct API test exercises `POST /api/recharge/intents` through Nest HTTP with a synthetic authenticated guard and the real commerce service gate: creation disabled returns 503 before intent write, billing call, or provider POST. A second test in the full Asaas real-DB suite uses a real account session and signed JWT against the real app and confirms the same 503/zero-provider-POST/zero-new-intent result. Phase 7 service tests cover the other flag combinations.

## Observability and alert contract

Application logs now emit fixed, non-identifying Asaas event codes for create attempts/blocks/success, sanitized provider HTTP/transport errors, webhook accepted/auth rejected/processing failed, reconcile-required, manual-review transition, and wallet credit success/failure. No token, API key, PIX payload, customer name/CPF, email, URL with query, or provider body is logged by these hooks. These process logs are **not** a configured monitoring platform, delivery guarantee, durable event store, or alert verification. Existing `OperationalEvent`, `PaymentWebhookEvent`, `AuditEvent`, reconciliation report, and wallet ledger remain the durable evidence. Confirm the real `bmapi` log path and retention before depending on the new log codes.

Future alert conditions (receiver and thresholds configurable; none invented here): any `PAID_WITHOUT_LEDGER_CREDIT` or duplicate-credit invariant breach is critical/immediate; any Asaas auth/transport failure sustained above an agreed count/window; webhook auth-rejection spike; `RECONCILE_REQUIRED` and `MANUAL_REVIEW` aging/backlog above an agreed count/age; a `PAYMENT_RECEIVED` event whose ledger credit fails; readiness 503 or webhook silence **only when payment traffic is expected**. Route alerts to an explicitly assigned finance/on-call owner, verify delivery and acknowledgment in a non-production environment, and test suppression when all Asaas controls are disabled. Log lines alone do not close this gate.

## Operator recovery — no blind financial write

1. In `/painel/admin/financeiro`, open **Reconciliacao** and `Verificar agora` (`GET /api/admin/finance/reconciliation`, `adminFinancialReportsView`). Identify `ASAAS_RECONCILE_REQUIRED`, paid-without-credit, or stale/manual-review rows; retain their IDs and timestamps in the existing restricted audit tooling, not in public logs.
2. Open the matching recharge detail/timeline. An ADMIN/SUPER_ADMIN with `adminOrdersOperate` may use **Ressincronizar com provedor** (`POST /api/admin/finance/recharges/:id/resync`) only with `ASAAS_RECONCILIATION_ENABLED=true` after a separately approved operational decision. It performs a provider **GET/search** by saved order ID or stable external reference, never a provider create POST. The provider/environment/reference/customer/amount/method are checked before any transition. The admin actor is propagated to the recharge status audit when a transition occurs.
3. If no matching payment is found, the record stays `RECONCILE_REQUIRED`; do not retry a provider POST just to clear it. Escalate with provider-side lookup and audit evidence. An amount/customer/order mismatch enters `MANUAL_REVIEW`, never forced WC credit. Unexpected provider state, chargeback or refund requires human finance/risk review; preserve webhook events, ledger, and audit. Do not treat a failed admin resync as evidence of no charge.
4. The webhook currently validates, stores/claims, queries the provider, reconciles and credits synchronously before returning 200. A provider 15-second timeout plus DB work can exceed a host/proxy/provider delivery window; duplicate delivery is idempotent, but **ACK timing is unverified**. Before registration measure p95/p99 and error/retry behavior on the real cPanel path. If too slow, design a durable inbox/worker with ACK only after durable claim; do not add an in-memory fire-and-forget queue.

## Isolated database rerun

An isolated Windows MySQL 8.0.46 instance and an isolated WSL MariaDB 11.8.6 instance were initialized from zero, each on its own loopback port and data directory; neither used the shared local database or a production credential. All 56 migrations applied on both. The seven selected real-DB suites cover Asaas provider/billing, health, Mercado Pago, reconciliation, wallet, and normal/deletion-request account paths. MySQL passed 77/77. MariaDB passed 76/77: the wallet concurrency test reproducibly fails on two simultaneous credits to an existing `AccountCurrency` row with MariaDB error 1020, “Record has changed since last read”; it failed again when that one suite was rerun alone. The other six MariaDB suites passed. This is a **real parity blocker**, not a reason to change the test expectation or silently retry a financial mutation inside an uncertain transaction. The current Phase 7B branch does not alter wallet concurrency semantics; a separately reviewed transaction/locking fix and rerun across supported MariaDB versions are required.

The Mercado Pago E2E fixture was updated to set its own explicit `MERCADO_PAGO_ENABLED=true` and `ASAAS_ENABLED=false`; the first combined run's MP failures were fixture configuration, not provider regression. After that correction, MP passed 17/17 in isolation without shell-supplied provider flags, and the full MySQL set passed 77/77. Billing encryption/key-version and synthetic-plaintext assertions, normal deletion and PRE_BETA_PURGE protection all passed in the selected MySQL suites. No real billing identity or provider key was used.

Both isolated DB listeners and the local API/preview processes were stopped after validation; the WSL MariaDB temporary data directory was removed and the Ubuntu MariaDB service installed for this test was stopped. The Windows MySQL test data directory `D:\MU\phase7b-mysql-5ffb4357725749df988827c2c72b77da` remains **offline**: this tool environment rejected its recursive removal even after the exact path was verified. It contains only synthetic test data, is not a running service, and needs a separately permitted cleanup; do not mistake it for the shared local MySQL data directory.

Remaining gates: resolve the MariaDB 1020 wallet concurrency failure and rerun; confirm the inferred old public API revision with a read-only host artifact/route inspection; verify cPanel webhook ingress/ACK/log/restart behavior and actual alert delivery.
