## INCIDENT: migration casing bug (`phase_v_progression_policy_status`)

**Root cause**: `apps/api/prisma/migrations/20260904090000_phase_v_progression_policy_status/migration.sql`
referenced the target table as `` `progressionconfigitem` `` (lowercase)
in its `ALTER TABLE` statement, while the actual table (created by the
prior migration `phase_u_progression_config_item`) is `` `ProgressionConfigItem` ``
(PascalCase). MySQL/MariaDB on Linux (production) is case-sensitive for
table identifiers; Windows local dev is not — so this bug was invisible
in every local test run and only surfaced against the real production
database. Same bug class as the earlier documented `open_beta_p0_foundation`
incident.

## Follow-up debt registered

`LINUX_CASE_SENSITIVE_MIGRATION_VALIDATION_REQUIRED` — Windows local dev
cannot detect table-name casing mismatches that a case-sensitive Linux
MySQL/MariaDB production host will reject. This is the second real
incident of this exact class (`open_beta_p0_foundation`, this one). A
static audit (grep-based, cross-referencing every migration's referenced
table names against canonical `CREATE TABLE` casing) was used as an
interim mitigation this round and found no other instances, but is not a
substitute for real case-sensitive validation. Future options: a CI job
running migrations against a real Linux MySQL/MariaDB container; a
pre-commit static casing-consistency check across all migration files.
Not implemented this round — registered as debt only.
