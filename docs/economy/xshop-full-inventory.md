# X-Shop Full Inventory (168 items) — Phase 14 Part A

**No X-Shop configuration was modified.** This is a read-only extraction and classification exercise. `KEEP?` starts `UNREVIEWED` on every row per instruction — this document does not decide removals, it prepares the evidence for Bryan to decide against.

## Source data

- `C:\MuServer\Data\Custom\CustomXShop.txt` — the 168-row catalog itself (`Category`, `ItemType`, `ItemIndex`, `ItemLevel`, option/socket/duration/price columns). Downloaded via `bm-remote.cmd download` (read-only RemoteOps), confirmed identical structure/row-count to Phase 12's original find.
- `C:\MuServer\Data\Item\Item.txt` — the base item definition table (name, requirements, damage, class-usability flags), newly downloaded this phase. `CustomXShop.txt` only carries numeric `ItemType`/`ItemIndex` keys; every item **name** in this report was resolved by joining against `Item.txt`, not invented or guessed from context.
- `C:\MuServer\Data\Custom\CustomShopBuyKits.txt` — a sibling shop-kit file, used only to establish the currency-column naming convention (see below). Not otherwise part of this inventory.

## Join result: 165/168 resolved, 3 honestly unresolved

165 of 168 rows matched a real `Item.txt` entry. The remaining 3 — **Axes, `ItemType=1`, `ItemIndex=9/10/11`** — have no corresponding row in `Item.txt`'s Axe block (which only defines slots 0–8 plus a disjoint slot 100 "BloodMoon Axe"). These 3 rows are reported as `ITEM=NOT_AVAILABLE` rather than guessed. This could mean the slots are genuinely unused/reserved indices in `CustomXShop.txt` (dead catalog rows that would fail to resolve to any real item if a player tried to buy them — worth an in-game purchase test before Open Beta), or that this server runs a `Item.txt` extension this environment doesn't have visibility into. **Not resolved further this phase** — flagged for a direct GameServer/in-game check, not assumed either way.

## X-SHOP ITEM IMAGE REQUIREMENT — confirmed blocker

Investigated whether item icon/texture assets could be safely exported for this review table. Finding, confirmed (not just a single-query signal):

- The four RemoteOps-allowed inventory roots (`C:\MuServer\Data`, `C:\MuServer\Tutoriais`, `C:\MuServer\GameServer\DATA`, `C:\MuServer\GameServerCS\DATA`) are exhaustively **server-side data** directories (drop tables, shop configs, item/skill/quest definitions, scripts). A targeted search for interface/texture/icon filename patterns (`Interface`, `Texture`, `Icon`, `Item.bmd`) across `C:\MuServer\Data` returned zero matches, consistent with `Data`'s known subdirectory listing from Phase 11/12 (`CashShop`, `Character`, `Custom`, `Event`, `Item`, `Lang`, `Maps`, `Monster`, `Shop`, `Skill`, `Terrain`, `Util`, …) containing no interface/texture folder at all.
- This matches the standard MU Online engine split: item icon textures (`.OZT`/`.OZJ`/`.bmd` visual assets) ship as part of the **game CLIENT** installation, a separate directory tree from the GameServer's data files. This session has no established, sanctioned read path into any client installation — `InventoryAllowedRoots` in `config\remoteops.json` names only the four server-side roots above, and RemoteOps is explicitly restricted to those.

**Exact blocker**: item icon/image export is blocked by missing access to the MU game client's asset directory, which is outside every root this session is permitted to read. This is an environment/access gap, not a technical impossibility — a future phase with an established, sanctioned path to a client install (or a GM willing to screenshot the in-game shop UI) could close it. **No fake or AI-generated images were created to fill the gap**, per explicit instruction. Every row's `IMAGE` column is set to `NOT_AVAILABLE_BLOCKED_NO_CLIENT_ASSET_ACCESS`.

## Currency columns — unconfirmed, carried forward from Phase 12

`CustomXShop.txt` labels its three price columns generically as `Coin0`/`Coin1`/`Coin2`, never naming them. The only sibling file that names an equivalent triplet explicitly is `CustomShopBuyKits.txt`, whose header reads `... KitId WCoinC WCoinP GoblinPoint` in that exact column order. By positional analogy, this report labels `Coin0≈WCoinC`, `Coin1≈WCoinP`, `Coin2≈GoblinPoint` — **this is an inferred guess, not a confirmed mapping**, and is repeated verbatim from Phase 12's own caveat rather than silently upgraded to a fact.

One more finding worth flagging to product: `WCoinC`/`WCoinP` (Cash vs. Points, a common two-currency split in this shop-kit convention) do not obviously correspond 1:1 to the single unified `WCOIN` `CurrencyCode` the portal's real economy (Phase 13) now uses. If `CustomXShop.txt` and `CustomShopBuyKits.txt` are ever wired into the portal, this split needs an explicit product decision — it is **not** assumed equivalent to portal WCOIN here.

## What "ItemLevel=13" and the excellent-option bitmask mean (inferred, not confirmed)

Every one of the 168 rows carries `ItemLevel=13` — a +13 upgrade level baked into the item at the moment of purchase, i.e. every X-Shop item is issued near the top of MU's +0..+15 upgrade scale, not as a base item a player then has to earn upgrades for. Every row also carries `ItemNewOption=63` (binary `111111`) in a field positionally consistent with a 6-bit excellent-option bitmask in this shop-file family — if that reading is correct, **every single X-Shop item ships with all 6 possible excellent options simultaneously active**, which by standard MU drop-rate math is a combination a player essentially cannot obtain through normal excellent-item drops (each drop typically rolls a random subset). This reading is **inferred from field naming and widely-documented MU private-server shop-file conventions, not confirmed against GameServer source or an in-game purchase test** — flagged as the single highest-confidence risk signal in the whole inventory, and called out per-row as `ALL_6_EXCELLENT_OPTIONS_INFERRED` rather than asserted as settled fact.

One genuine, easily-missed exception: the **Swords** category (12 items) carries `ItemDuration=60` — i.e. those 12 items are **60-day rentals**, not permanent grants, unlike every other one of the 13 remaining categories (`ItemDuration=0`/permanent). This is a real, non-obvious asymmetry in the existing catalog worth carrying into any future design.

## Risk classification taxonomy used in the table below

- `CURRENT_RISK` — objective, evidence-based tags derived directly from the row's own data (upgrade level, excellent bitmask, harmony, socket count, req. level bracket, server-exclusive naming). Never a judgment call.
- `RECOMMEND` — a *separate, non-overwriting* column suggesting a starting point for review, deliberately **not** collapsed into a blanket "remove everything +13" rule per instruction:
  - `RECOMMEND_REMOVE_OR_GATE_ENDGAME_FULL_EXCELLENT` — high base req. level (≥150) or a server-exclusive named item, *and* the all-excellent bitmask. Highest-confidence "this is overpowered for direct sale" signal.
  - `RECOMMEND_REVIEW_ENDGAME_ITEM` — high base req. level alone.
  - `RECOMMEND_REVIEW_FULL_EXCELLENT_PLUS_SOCKET` — all-excellent bitmask plus a socket, on an otherwise mid-tier item.
  - `RECOMMEND_LOW_RISK_STARTER_TIER_CANDIDATE_KEEP` — low base req. level (≤90), most often accessories with no level requirement at all — genuinely low-impact even at +13/all-excellent.
  - `RECOMMEND_REVIEW_UNCLASSIFIED` — the large middle bucket (163/168 rows): mid-tier base items (req. level roughly 90–150) that are not automatically low-risk *nor* automatically endgame. This is where the instruction's "do not pre-judge every +13 item" applies most directly — these need a human (product/GM) judgment call informed by actual in-game power context this document cannot fully supply from static config alone.
- `KEEP?` — always `UNREVIEWED`. Reserved for Bryan/product to fill in per row.
