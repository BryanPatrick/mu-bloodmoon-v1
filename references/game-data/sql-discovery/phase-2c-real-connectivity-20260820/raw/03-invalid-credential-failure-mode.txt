Command: D:\MU\Tools\RemoteOps\bm-agent-probe.ps1 -MembGuid 3 -SimulateBadCredential
Purpose (Part I): prove the real Agent code path (Microsoft.Data.SqlClient,
not bm-sql) fails gracefully on an invalid credential -- no crash, no
hang, a clean typed exception, nothing sensitive echoed.

The real bloodmoon_observer username was sent with a deliberately wrong,
fixed dummy password ("deliberately-wrong-test-credential") instead of
the real credential -- the real credential was never weakened, exposed,
or reused incorrectly; this only exercises the login-failure path.

Raw stdout (sanitized JSON):
{"overall":"FAIL","sqlClientConnection":null,"snapshotStatus":null,"accountId":null,"online":null,"activeCharacterMasked":null,"cashShopPresent":null,"warehouseMoney":null,"characters":null,"inconsistencyReason":null,"errorType":"SqlException","errorMessage":"Login failed for user 'bloodmoon_observer'."}

Process exit code: 2 (non-zero, distinguishable failure -- not a silent
success, not a hang, not a crash without exit).

Findings:
- The real SqlException is caught and reported cleanly (errorType +
  a short driver-provided message) -- no connection string, no password,
  no stack trace in the output.
- No SQL Server-side lockout or side effect: a single failed login attempt
  against a standard SQL login has no destructive consequence; this was
  not repeated beyond what was needed to observe the failure path once.
- This exercises the same exception-handling path
  BloodMoon.GameBridgeAgent.Tools.ConnectivityProbe.Program.Main's
  try/catch does; the production Agent's own AgentWorker poll loop wraps
  reader calls in comparable exception handling already covered by
  Phase 1's AgentWorkerTests (send-failure retry, no crash-loop) -- this
  real test specifically closes the "invalid credential" gap in that
  matrix using the real live server, without needing to take the
  production SQL Server itself offline (which would be a destructive,
  out-of-scope action).
